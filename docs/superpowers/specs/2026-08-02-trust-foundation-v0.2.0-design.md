# Crypto Signal Terminal v0.2.0 交易可信度基础设计

## 目标

让每一条可执行机会都基于当前币种自身的健康行情，而不是一个可能被其他数据流覆盖的全局状态；同时让模拟订单在服务重启后仍可审计，为后续复盘和策略校准建立可靠数据基础。

## 范围

本轮包含：

- 按币种记录健康、降级、不可用和最后观测时间。
- 扫描失败保留明确原因，不再静默吞掉后把单次成功当成全局健康。
- 准备模拟订单时在服务端复核机会自身健康、当前币种健康和数据年龄。
- 将模拟订单写入现有本地审计数据库，并提供只读历史接口。
- 桌面端显示健康覆盖率、所选币种健康状态和具体订单拒绝原因。
- 版本升级到 `0.2.0`，更新发布说明。

本轮不包含：

- 新策略、Dune 后台调度、宏观新闻或 OCR。
- 真实交易所下单、自动交易或交易所私钥。
- 完整回测平台和策略收益归因；本轮只建立其所需的可信数据基础。

## 方案比较与选择

### 方案 A：只修复全局布尔状态

改动最小，但仍无法解释哪个币种失败，也无法阻止旧机会在其他币种恢复后被错误放行。

### 方案 B：逐币种健康注册表加持久化订单日志（采用）

在现有 `ApplicationState` 旁增加职责单一的健康注册表；扫描器和 Telegram 协调器只报告各自观察，订单 API 按机会币种复核。复用 `AuditStore` 保存模拟订单，形成从数据质量到订单审计的完整闭环。

### 方案 C：重写为完整事件溯源系统

长期扩展性最好，但会显著扩大 v0.2.0 的迁移风险，不符合当前先增强可信度的目标。

## 架构

`MarketHealthRegistry` 维护 watchlist 和每个币种的最新状态。扫描成功写入交易所 `DataHealth`，失败写入受控错误分类；整体状态由注册表派生，Telegram 单币种成功只能更新该币种，不能直接覆盖整体状态。

`POST /api/v1/paper-orders` 依次校验：机会存在且有订单计划、计划未过期、机会原始数据健康、当前币种状态健康、最新健康观测未超过 30 秒。通过后生成稳定订单 ID，写入 SQLite，再返回记录。`GET /api/v1/paper-orders` 返回最近记录，不返回任何秘密。

前端 `Health` 类型增加逐币种摘要。顶部状态栏显示健康覆盖率，信号画布显示当前币种是否可交易。订单失败时展示服务端返回的具体中文原因。

## 数据与错误边界

- 健康状态只保存公开市场元数据，不保存凭据。
- 对外错误不包含上游响应正文、令牌或堆栈；只使用 `timeout`、`upstream_error`、`invalid_payload`、`unknown` 等分类。
- 数据年龄以带时区的 UTC 时间计算；未来时间戳视为零年龄，但不会绕过 `healthy` 校验。
- 历史接口默认最多返回 50 条，服务端硬上限 200 条。
- 数据库写入失败必须拒绝订单，不能返回“已准备”。

## 测试与验收

- 扫描器部分失败时，成功币种保持可交易，失败币种不可交易，整体为降级。
- Telegram 单币种成功不会把其他失败币种或整体状态错误改为健康。
- 订单 API 拒绝过期、原始数据不健康、币种降级和健康观测过旧的机会。
- 合格订单写入 SQLite，重建应用后仍能通过历史接口读取。
- 前端显示覆盖率、所选币种状态和后端拒绝原因。
- Python、React、Rust 测试和生产构建全部通过。

## 发布

版本号统一升级为 `0.2.0`。创建 GitHub 远程仓库，推送默认分支，打 `v0.2.0` 标签，并创建包含校验信息的 GitHub Release。发布仍明确标注为本地模拟订单软件，不支持真实资金执行。
